# Use one database for Foundry persistence

Foundry stores all persistent product data in one `foundry.sqlite` database per operating-system user. Its directory is resolved with `env-paths('foundry', { suffix: '' }).data`, using the platform application-data convention; a relative Linux `XDG_DATA_HOME` is ignored as invalid. Every Foundry-owned table uses a Node-generated UUIDv7 `id` plus Unix-millisecond `created_at`, `updated_at`, and nullable `deleted_at` fields; database-internal and migration metadata tables are exempt, and ordering by creation time uses `created_at` rather than assuming UUIDs are strictly monotonic. Database migrations have their own ordered history independent of CLI versions: a release adds a migration only when schema or stored data changes, and repeated startup applies nothing after the history is current. Before applying all pending migrations, Foundry creates an online SQLite backup in the data directory's `backups` subdirectory and, after that backup succeeds, retains only the newest backup. A CLI refuses to open a database containing migrations it does not know; corruption, incompatible migration histories, and failed migrations are application-wide failures rather than reasons to substitute default data.
